TECH 3498 / ASSIGNMENT 3
Secure Web Architecture — Design Write-up
Application: Cybersecurity Research Workbench. Design objective: allow students to explore labs and save reports while protecting identities, report ownership and stored data.
The proposed architecture separates the frontend, web server, application layer and database. The HTML/CSS/JavaScript frontend communicates through HTTPS with an Nginx reverse proxy. The proxy serves static content and forwards API requests to a private Node.js application. Only the application may query the private PostgreSQL database. This separation limits public exposure and gives each layer a defined responsibility.
Authentication uses an OpenID Connect provider, with MFA for administrators. Authorization is a separate application decision: students access their own reports, instructors review assigned students, and administrators manage accounts. Every request must pass role and ownership checks, regardless of what the interface displays.
Encryption protects traffic with TLS and protects database volumes and backups with managed encryption keys. Opaque session cookies use Secure, HttpOnly and SameSite attributes; server-side records support expiry, rotation and immediate logout revocation. CSRF tokens and Origin checks protect state-changing requests.
Server-side input validation restricts request types, fields, sizes and formats. Parameterized queries keep data separate from SQL instructions, while safe DOM rendering and contextual output encoding prevent untrusted text from becoming executable markup. Redacted audit events support investigation without retaining passwords, API keys or session tokens.
Security is incorporated at each trust boundary rather than delegated to the frontend. The current single-file website demonstrates security concepts; the proposed private services and enforceable backend controls still need implementation. Verification would include cross-user access tests, revoked-session checks, injection payload tests and backup restoration.

05 / ASSIGNMENT 3
Secure Web Architecture
Designing a trusted path from the browser to the data.
Proposed architecture. This workbench currently runs as a browser-based educational simulation. The server, database, identity provider, and server-side controls below describe a future deployment; they are not implemented by this page.

  
One request. Four layers of responsibility.
The browser is untrusted. Each boundary validates the request again before granting access.

    
    
      
  1. 01 / PUBLIC CLIENT
    Frontend
    HTML, CSS and JavaScript
    Accessible interface; no secrets
    ↓ HTTPS / TLS
    2. 
      
  2. 02 / PUBLIC EDGE
    Web server
    Nginx reverse proxy
    TLS, limits, security headers
    ↓ Private, authenticated TLS
    3. 
      
  3. 03 / PRIVATE SERVICE
    Application layer
    Node.js API
    Identity, permissions, validation
    ↓ Parameterized SQL over TLS
    4. 
      
  4. 04 / PRIVATE DATA
    Database
    PostgreSQL
    Least privilege; encrypted storage
    ↑ Minimal authorized results
    5. 
    
Supporting services: an OpenID Connect identity provider authenticates users; a private Redis store holds sessions; a secret manager supplies service credentials; a restricted audit service records security events. The browser never connects directly to the database or session store.

  

  
Security built into every component

    
01
Frontend
The interface collects inputs and displays results. Client-side validation helps users correct mistakes, but the API makes every security decision. Render untrusted text using safe DOM methods and contextual output encoding. Bundle reviewed dependencies and deploy a restrictive Content Security Policy.
Addresses: DOM injection and accidental secret exposure.

    
02
Web server
The reverse proxy serves static assets and forwards only intended API routes. Redirect HTTP to HTTPS; enable HSTS after HTTPS is correctly deployed. Restrict request sizes, timeouts, and request rates. Keep the application and data services off the public network.
Addresses: transport interception and resource exhaustion.

    
03
Application layer
The API applies session checks, authorization and schema validation before business logic. Use structured errors without stack traces, redact secrets from logs, and audit denied access and privilege changes. Keep optional AI provider credentials on the server; treat AI responses as untrusted data, never as permission to run tools.
Addresses: bypassed controls and unintended data disclosure.

    
04
Database
Store users, owned lab reports and coursework metadata in PostgreSQL. Reports reference an owner ID; enforce foreign keys and data constraints. Use parameterized queries and a restricted application account, with a separate migration account. Encrypt backups, restrict their access and test restoration.
Addresses: SQL injection and excessive database privileges.

    
05
Authentication
Delegate sign-in to an OpenID Connect provider using the authorization-code flow with PKCE. The backend verifies issuer, audience, signature, expiry, state and nonce. Require MFA for administrators. Apply login throttling and generic failure messages. Store the provider subject ID rather than collecting passwords in this application.
Addresses: account impersonation and credential attacks.

    
06
Authorization
Deny access unless an explicit policy permits it. Students can read and edit their own reports; instructors can review assigned students; administrators manage accounts and roles. Check role, assignment relationship and record ownership on every API request. A hidden button or guessed report ID never grants access.
Addresses: broken access control and cross-user data access.

    
07
Encryption
Use TLS for browser-to-edge and service-to-service traffic, with certificate verification. Encrypt database volumes and backups using managed keys with restricted access and rotation. Store secrets in a secret manager. Password hashing, if later required for local accounts, is a separate one-way operation—not reversible encryption.
Addresses: intercepted traffic and exposed stored data.

    
08
Session management
After sign-in, issue a cryptographically random opaque session ID in a Secure, HttpOnly, SameSite=Lax cookie with Path=/ and no Domain attribute. Store session state server-side. Rotate the ID at login and privilege changes; enforce a proposed 20-minute idle and 8-hour absolute timeout. Logout revokes the server session. Protect state-changing requests with CSRF tokens and Origin checks.
Addresses: session fixation, replay after logout and CSRF.

    
09
Input validation
Validate every API request against a server-side schema: expected types, allowed fields, length limits, formats and ranges. Reject unexpected fields and oversized payloads. Use parameterized SQL for database access and context-appropriate encoding when returning content. Validation, SQL parameterization and output encoding solve different problems and must work together.
Addresses: malformed requests, injection and unsafe rendering.

  

  
Walkthrough: a student saves a lab report
  1. The browser sends an HTTPS POST with its session cookie, CSRF token and report data.
  2. The reverse proxy checks request limits and forwards the request to the private API.
  3. The API verifies the live session, CSRF protection and input schema. It derives the owner from the session, not a client-supplied owner field.
  4. For an update, the API checks the student's ownership of the existing report. Unauthorized access is rejected without returning the report.
  5. A parameterized database transaction saves permitted fields. The API records a redacted audit event and returns only the authorized result.

  
How the proposed controls would be verified
  • An unauthenticated API request is rejected; expired and revoked sessions cannot be reused.
  • Student A cannot read or update Student B's report, including by changing a URL or request body.
  • Requests with missing CSRF tokens, invalid schemas or oversized bodies are rejected.
  • SQL metacharacters remain data; HTML payloads render as text without execution.
  • The database is unreachable from the public network; service certificates are verified.
  • Backups restore successfully and logs contain no credentials or raw session tokens.
These are proposed acceptance checks, not claims that a backend has been deployed or security-tested.
